## 四、签名体系（三条链路共用，重点）

**结论：x-s / x-t / shield 等签名头全部在 native 层生成，Java 层只有壳。** 全仓 11.4 万类中不存在 `"x-s"`/`"x-t"` 字符串字面量（已全量 grep）。两套独立机制：

### 1. Tiny 签名（主 API 链，产出 x-s/x-t 系头）

- Java 拦截器 `TinyInterceptor`（`n0c/p.java:30`），注册在主 API client 拦截器链（`hjc/n1.java:123-131`、`hjc/j2.java:1525`）
- 流程（`n0c/p.java:142-184`）：加 `x-legacy-did/fid/sid` 三个头 → 读请求体 → 调 `idb.f.h(method, url, body)`（`:86`）→ `com.xingin.tiny.internal.j3.b(-1765467163, method, host, path, query, body)`（`idb/f.java:149`）→ **`t.a(...)` native 方法（`com/xingin/tiny/internal/t.java:85`）→ `libtiny.so`（及 tinyd）**
- 冷启动首刷优化：`launch_scenario=1` 的 homefeed 请求优先用缓存签名（`TinyTokenHelper.getCacheSignMap()`，`n0c/p.java:155-168`）；响应码 **462 = 签名失效**，清缓存重签（`:176-183`）
- 作用域：只对 `*.xiaohongshu.com` / `*.rnote.com` 且非 multipart 的请求签名（`hjc/n1.java:675-692`）

### 2. Shield 签名（libxyass.so，全 native 拦截器）

- Java 拦截器 `com/xingin/shield/http/XhsHttpInterceptor.java:14`：`intercept()` 直接调 `Native.intercept(chain, cPtr)`（`:106`），整个拦截（含加 `shield` 头）在 native 完成
- 库名：`com/xingin/shield/http/c.java:37` `byte[]{120,121,97,115,115}` = ASCII **"xyass"** → **`libxyass.so`**（`:70` SoLoadProxy 加载）；初始化 `hjc/n1.java:668-673`（deviceId、appId=-319115519）
- 旁证：剥离拦截器 `yq9/v.java:19-29` 在特定场景移除 `shield`、`xy-common-params`、`xy-platform-info`、`x-mini-mua/sig/gid`、`x-legacy-*`、`x-xray-traceid`、`X-B3-TraceId` —— 证明这些头由上游（native）统一注入

要重放/模拟这三条链路的请求，需对 `libxyass.so`、`libtiny.so` 做 native 分析（本机已装 Ghidra 12.1.4 + rea 可承接）。`.so` 在 APK `lib/arm64-v8a/` 下，未经脱壳即可读（App 未加固）。预计工作量：shield 的 `Native.intercept` 算法还原 + Tiny 的 `j3.b` 参数结构，属独立战役。

## 七、请求 URL 拼装与 xsec_token（补充调查）

### xsec_token 是什么

每篇笔记的**服务器下发字段**，客户端**从不生成**。在响应模型中的落点：

| 模型 | 字段 | 证据 |
| --- | --- | --- |
| 推荐/首页 `NoteItemBean` | `@dd.c("xsec_token") String xsecToken` | `entities/NoteItemBean.java:554` |
| 搜索 `SearchNoteItem` | 同名私有字段 + `getXsecToken()` | `alioth/entities/SearchNoteItem.java:215`、`:3183` |
| 搜索广告 `alioth/entities/h` | 同名字段 | `alioth/entities/h.java:90` |
| 预加载项 `q1`（NotePreParam） | 同名字段 | `entities/q1.java:15` |

### 它在 App 里怎么流动

1. **App 内跳转详情：不走 URL query 参数。** 搜索结果/feed 点击时，`AliothRouter.enterNewNoteDetail` 用 `p0.b(searchNoteItem)` 把搜索结果转成 `NoteItemBean`（token 随字段携带），整个 bean 作为 Serializable extra 放进导航 Bundle（`AliothRouter.java:103-157` 的 `wVar` 构造）。路由参数类 `p2a/w.java`（`xhsdiscover://portrait_feed`）的 URL 参数清单里**没有** xsec 字段——`id`、`sourceId`、`index`、`feedType`、广告参数等，token 只随 bean 对象走。
2. **deeplink 打开分享链接**（`xhsdiscover://item/<id>?xsec_token=…`）：路由 `coc/y.java` 不单独解析 xsec_token，它随 `key_raw_url` 原始 URL 字符串透传。
3. **唯一明确消费点：详情预加载**。`/api/sns/v1/note/detailfeed/preload` 的 `data` 参数是 JSON 数组，每项为 `{id, type, ext, xsec_token}`（`matrix/detail/utils/NotePreLoadUtils.java:330` 构造 `new q1(..., preloadAble.e())`，`q1.java:15` 的 `@dd.c("xsec_token")`）。`NoteItemBean` 通过 `preLoadInfo.h/g(id, type, xsecToken, …)` 把 token 送入预加载（`NoteItemBean.java:1714-1716`，搜索侧 `SearchNoteItem.java:3030`）。
4. **分享链接里的 xsec_token 也是服务器拼好的**：分享信息模型 `ShareInfoDetail` 的 `link`/`innerLink` 字段（`entities/ShareInfoDetail.java:26-27`）由服务端响应直接给出完整 URL，客户端不拼。

### 关键结论：详情主请求不依赖 xsec_token

- 详情 API（`/api/sns/v1/note/imagefeed`、`/api/sns/v4/note/videofeed`）的显式参数中**没有 xsec_token**（`NoteInitialParamsKt.java:14` 的参数清单、`NoteDetailService.java:177-179`、`VideoFeedNetService.java:25-28` 均可证）。它可能随 `source_params`/`search_extra_params` 等 JSON 上下文带入，但不是独立必填项。
- 也就是说：**xsec_token 主要是 H5/网页端与预加载场景的校验令牌；App 端请求的合法性由 Tiny（x-s/x-t）+ Shield（libxyass）签名体系保证**，而不是 xsec_token。抓 App 包看到请求里没有 xsec_token 是正常的。
- 对重放/模拟请求的含义：拼 URL 时不需要造 xsec_token；真正绕不开的是两个 native 签名（libtiny.so 的 `j3.b` 与 libxyass.so 的 `Native.intercept`）。

### 请求 URL 拼装方式（通用模式）

- 接口声明用 skynet 注解：`@hcd.f("api/sns/...")` 路径 + `@hcd.t("param")` query（Retrofit 风格），host 由网络模块配置（`edith.xiaohongshu.com`）。
- 参数来源三类：(a) 显式 query 参数（如上各表）；(b) JSON 上下文字符串参数（`source_params`、`search_extra_params`、`known_signal`、`rec_params` 等，由上游页面状态序列化）；(c) header（`xy-common-params` 公共参数头 + Tiny/Shield 签名头，native 注入）。
