## 二、重打包（gadget 注入）经验

官方 APK 未加固（14.6 万类直接 jadx 可读），重打包路线：

1. frida-gadget 版本必须对齐宿主机 frida（17.23.3），GitHub releases 下载 android-arm64
2. **apktool 3.0.3 大坑**：解出的约 9300 个 layout XML 带空前缀声明（`xmlns:android=""`），aapt2 拒绝编译。需批量修复（未用前缀删除 15621 处 + 使用中重映射 558 处）。`apktool d -r` 不可行——Manifest 保持二进制就改不了包名
3. 包名手术式替换 `com.xingin.xhs` → `com.xingin.xhsre`：package/authorities/permission 声明与引用都改，组件类名不动。与官方包共存，不碰用户数据
4. 注入点：`XhsApplication.attachBaseContext` 开头 `System.loadLibrary("frida-gadget")`，并用 `ActivityThread.currentProcessName()` 判断**只在主进程加载**（否则 pushservice 等子进程抢 gadget 端口/卡死）
5. gadget 配置 `libfrida-gadget.config.so`：listen `127.0.0.1:27043`（避开 27042 特征端口），`on_load=wait`（App 冻结到 frida 连上，保证 exit 封堵先于看门狗生效）
6. **签名校验对策**：从原 APK v2 签名块解出证书 DER，算得原 `Signature.hashCode = -1083242518`；sign.js 检测到非官方包名时自动 hook `android.content.pm.Signature.hashCode` 返回该值
7. 小米安装限制：MIUI「USB 安装」开关默认关，`adb install` 静默报 `INSTALL_FAILED_USER_RESTRICTED`（无弹窗、15s 自动取消）。需用户在 开发者选项 里手动打开（要求小米账号+SIM 卡）

## 三、已知问题

### 1. 反复拉起 App（待改进）

gadget `on_load=wait` 下 App 启动即冻结等 frida；反调试看门狗杀进程后，客户端的自动重连逻辑会 monkey 重新拉起，形成"反复弹出小红书（RE）"的现象。因为副本沿用了原应用名/图标，视觉上与官方版无法区分，体验很差——本次真机验证因此中断。

改进方向（未实施）：
- 应用名改「小红书RE」已完成（14:20 构建版）
- 客户端重连逻辑应加：最大重试次数 + 指数退避 + `--no-relaunch` 开关
- 更彻底：把 sign.js 作为 gadget script-interaction 打进 APK（`libfrida-gadget.script.so`），App 自启动自加载脚本，不需要外部 attach，消除冻结窗口和拉起循环

### 2. 看门狗升级

最初检测到 frida-server 走 `_exit(0)`（可封堵：frida 脚本加载后第一时间 `Interceptor.replace` libc `exit`/`_exit`，调用线程睡死）；后来偶发升级为**野指针 SIGSEGV** 杀进程，无法封堵，只能靠进程死亡检测 + 自动重 attach 续命。

### 3. 服务端风控

- 登录接口在模拟器/数据中心 IP 下稳定被拒：`300012 IP存在风险` / `300015 浏览器运行环境异常` / `406 + xy-ter-str`（shield 密钥轮换挑战，轮换后仍 406）。**这些是风控评分而非签名错误**（签名错误返回 461 签名类错误码；同管线 basic homefeed 始终 200）。真机住宅网络大概率放行，待验证
- 游客态（仅 activate session）可调首页，搜索/详情返回 `-100 登录已过期` 或 406 空数据——需正式登录的 `x-legacy-sid`

## 四、frida 17 适配清单（通用经验）

- frida 17 不再内建 Java 桥：需复刻 frida-tools REPL 的 `frida:load-bridge` 协议手动加载（`client/java-bridge.js`）
- `Module.getExportByName` → `Module.findGlobalExportByName`
- jadx 消歧字段名（如 `f216243e`）运行时真名是末字母（`e`）；字段与方法同名时桥优先解析成方法——**统一走反射访问**
- 反射 `invoke` 返回的包装器按声明类型 `Object` 解析方法，需 `Java.cast`
- `Java.registerClass` 实现接口时：不能返回"存全局的 Java 对象"（须在方法里现造）；回调参数是借用包装器，跨调用持有须 `Java.retain`
- 静态方法 `overload(...).call(null,...)` 会触发桥 bug，应让桥按参数类型自动选重载
- 给 native 层喂构造不完整的假对象（如无 body 的 dummy Response）会导致 JNI abort 崩进程
- App 进程会 prctl 改名为 `rednote`，按包名 attach 找不到，用 `pidof`
