# 真机迁移与现场情况（含经验教训）

> 2026-10-13 大更新。本文记录：真机路线从"反复拉起崩溃"到"全链路签名可用"的完整排障过程与最终架构。

## 一、最终架构（已验证）

```
xhs_api.py (Mac)
   │  JSON 行协议，经 adb reverse tcp:27045
   ▼
内嵌脚本（libfrida-gadget.script.so，gadget script-interaction 形态）
   │  随 App attachBaseContext 自加载，主动反向连 Mac
   ├─ 生存 hooks：exit/_exit 睡死 + abort 吞掉（native，最先装）
   ├─ Signature.hashCode 早期钩（Java.vm.perform 绕过 ClassLoader 延迟队列）
   ├─ sign.js 全部签名逻辑（tiny/shield/x-legacy-*/xy-common-params/假 Chain）
   └─ 反向连接 + 行分隔 JSON 分发（dispatch → rpc.exports）
```

**为什么是这个形态**：listen 模式有两个死穴——① 外部 attach 有竞态，完整性校验 ~1.4s 就 abort，钩来不及装；② 进程内监听端口本身就是 watchdog 检测面。script 模式自加载零竞态、零监听（反向出站连接），两个死穴一起消失。

## 二、"反复拉起"的完整根因链（重要复盘）

表面现象是反复拉起，实际是**四层问题叠加**，逐层挖完才根治：

1. **Java 崩溃 1（SplitLoadManagerService 未初始化）**：小红书用 Play Core splitInstall，`XhsActivity.getResources` 里调 `SplitInstallHelper.loadResources`。改包名后插件框架 Petal 没初始化 → 崩。修：smali 给三处 `loadResources` 调用包 try/catch（单 APK 资源是全的，跳过无损失）。
2. **Java 崩溃 2（i52.h NPE）**：语言上下文的静态 Application 字段为 null。根因是**主进程判定硬编码** `Intrinsics.areEqual(processName, "com.xingin.xhs")`（`a1c/a.smali`）——包名一改主进程判定失败，attachBaseContext 走了子进程分支早退，Petal、语言环境全没初始化。修：8 个 smali 文件里的进程名比较常量改成新包名（其余 43 处字符串是 SP 名/authority 等，不动）。
3. **SIGABRT（完整性校验）**：libxyass `initializeNative` 读 APK 签名哈希比对白名单，重打包签名不符 → 匿名内存（dexvmp 解密代码）调 abort。修：`Java.vm.perform` 早期钩 `Signature.hashCode` 返回原包哈希 -1083242518（官方 v9.36.2 证书 DER 算得）。钩上之后**连 abort 都不再发生**——证明判断准确。
4. **SIGSEGV 升级**：吞掉 abort 后同一段匿名代码用野指针继续杀进程。第 3 步修好校验后不再触发。

另外 gadget `on_load=wait`（App 冻结等 frida）+ 客户端无上限重连 = 拉起风暴的放大器；现在 on_load 无关（script 模式立即跑）、客户端重连限 3 次带退避。

## 三、frida 17 / gadget 适配清单（通用经验）

- frida 17 无内建 Java 桥：attach 形态走 `frida:load-bridge` 协议要主机应答；**script-interaction 形态没有主机**，必须把 java-bridge.js 源码直接内联进脚本再 `Object.defineProperty(globalThis, 'Java', ...)`。
- **`Java.perform` 的 ClassLoader 延迟队列**：app 进程 ClassLoader 未就绪时 perform 排队不执行（等 ActivityThread 就绪才跑）。早期 hooks（框架类即可的）要走 `Java.vm.perform` 直挂当前线程。
- **`rpc` 是 frida 运行时保留全局**：脚本里 `var rpc = {exports:{}}` 会撞上它导致加载期静默中止。要复用带 `rpc.exports = {...}` 的现成脚本，直接用内置 rpc 全局即可。
- gum `Socket.listen` 能 bind（netstat 可见 LISTEN）但 **accept 的 promise 不派发**（gadget script 模式实测）；`Socket.connect` 出站正常 → 用反向通道（adb reverse）。
- gum 无 TextEncoder，UTF-8 编解码要手写。
- 真机无 root 时 shell 读 /proc/<pid>/maps 可能静默 EACCES 返回空——别拿它当"没加载"的证据（我们被这个误导过一轮）。

## 六、第二次会战（2026-10-13 晚）：搜索 API 打通 + 稳定性攻防

目标：登录后**不碰手机**，Mac 直接调搜索/详情 API。最终形态：App 当"代理执行器"，Mac 只发参数。

### 6.1 两条设备内通道（sign.js 新增 RPC）

| RPC | 原理 | 结果 |
|---|---|---|
| `fetch` | Java.choose 找到带 `n0c.p`(TinyInterceptor)+`XhsHttpInterceptor` 的 OkHttpClient 实例（edith 专用客户端），`client.newCall(req).execute()` | **鉴权全通**（搜索 200 真实数据）；但触发静默杀进程概率高 |
| `rawfetch` | 先 `sign` RPC 算全套头（tiny/shield/legacy/commonParams），再用 HttpsURLConnection 从手机发出 | **稳定不死**；guest 接口（basic homefeed）200；登录态接口报"登录已过期"；登录接口 461+300015 |

要点：gum 的 JS 线程 Java 栈只有 ~1MB，整条拦截器链必 StackOverflowError——fetch 必须丢进 `Executors.newSingleThreadExecutor()` 的 Java 线程跑（`Future.get()` 等结果）。

### 6.2 406 与"登录已过期"的真相

- 客户端之前从 Mac 直连：登录 406→轮换→406 循环。实为**两层叠加**：①shield 密钥轮换本身有效但 Mac 出口 IP 已被标记（登录接口 461+300012 "IP存在风险"）；②改从手机发出后变 461+300015 "浏览器运行环境异常"——**登录接口有环境风控，只有 cronet 原生栈的请求才带齐信任信号**。
- 搜索等已登录接口：Mac 直连与 rawfetch 都拿到 200 + `{"code":-100,"msg":"登录已过期"}`。这是**软拒绝**——不是 sid 过期（App 内 UI 登录后马上取新 sid 也一样），而是请求缺 cronet 路径的某些信任成分（疑似 TLS/HTTP 指纹或拦截器附加头）。**用 appFetch（App 的 OkHttpClient 全真链）则鉴权完全通过**。
- 附加头发现：`jjc/r.java` 给 edith 请求加 `x-access-token`(UserInfo.getUserToken) / `x-user-id` / `x-platform-info=3` / `x-app-version` / `x-device-id`。但即使补上这些头，rawfetch 仍被软拒——差异在更底层（传输指纹）。

### 6.3 搜索接口参数表（缺参会 500 NPE）

`/api/sns/v10/search/notes` 的参数构建器是 `rc0/h.java`（jadx 全量可读）。服务端对缺参的报错是 RPC 层 NPE（`SearchNoteSolution.getGenericResult() is null`），不是参数校验错误。最小可用集（已验证 200 + 20 条）：

```
keyword, filters="", sort=general, page, page_size=20, source=explore,
search_id=<uuid32>, session_id=<uuid32>, api_extra="", page_pos=0,
ext_params="", pin_note_id="", allow_rewrite=1, geo="", loaded_ad="",
query_extra_info="", rec_extra_params="", scene=search, is_optimize=0,
location_permission=0, device_level=2, refresh_type=1, exp_infos="",
feed_oaid="", known_signal="", ai_mode=0, search_tab=notes
```

返回结构：`data.items[]` = `{model_type:"note", mix_track_id:"NOTE__<note_id>__...", note:{note_id?, xsec_token, title, images_list, user, interact_info,...}}`。**xsec_token 就在搜索结果里**（当初逆向 xsec 生成逻辑的必要性至此解除）。客户端解析器：`XhsClient.parse_search_items()`。

### 6.4 稳定性攻防（看门狗猫鼠游戏）

App 会周期性无痕自杀（无 tombstone、无 AMS 日志），逐层挖出：

1. **libmsaoaidsec.so+0x1c154**：MSA OAID SDK 读 /proc 下文件做字符串比对，不符 → `exit(0)`/`_exit(0)`。libc 层钩住后拿到调用点（frida `Process.findModuleByAddress(this.context.lr)`），**二进制 NOP 掉两个 `cbnz x0, →自杀` 分支**（va 0x1c0e8/0x1c0f8）根治。
2. **中和钩的正确写法**：exit 家族/abort 用 `Interceptor.replace` + NativeCallback 直接返回（干净 C 返回）。**教训**：①睡死线程（Thread.sleep(24h)）会让主线程冻结被 MIUI 以 APP_SCOUT_HANG 无痕 SIGKILL；②`Interceptor.attach` + `pc=lr` 跳函数体会破坏运行时状态（比 replace 更容易留后遗症）。
3. **kill/tgkill 降级**：SIGKILL/SIGTERM 改信号 0。**必须放行信号 32/33**（ART GC 挂起用），全中和会把运行时打残。
4. **syscall 直通监控**：钩 `syscall`，nr∈{93,94,129,131} 记来源改 getpid(172)。（至今没抓到——说明还有一个用**内联 svc** 的杀手没找到，进程仍有 ~40-90s 生命周期窗口，死后 App 会自愈重启，客户端 `_reattach` 重连重试即可。）
5. **debuggable=true 是坑**：会开 CheckJNI，frida 桥的边角 JNI 调用从"警告"变"致命"，且 ART 打印崩溃栈时自身 SEGV（Throwable::Dump→vsnprintf 崩）。排查完记得去掉。
6. **多进程抢线**：gadget 在每个进程（:pushservice/:longlinkNew…）都加载，都跑反向连接会互相顶线（BrokenPipe 之源）。脚本开头读 `/proc/self/cmdline`，非主进程跳过 server 段。**注意 frida 的 `File.readBytes(size)` 只收字节数返回 ArrayBuffer**，传 buffer 会报 "expected an unsigned integer"。

### 6.5 仍未解决（诚实清单）

- **rawsvc 杀手**：libc/syscall 层全埋了钩子仍有无痕死亡，疑似 dexvmp 匿名内存里的内联 svc exit_group。下一步可用 Stalker 或在 libargus/libsecurebase 里静态找。
- **登录 API 直连 300015**：UI 登录一次后 API 全通；纯 API 登录被环境风控挡。若要去掉 UI 这一步，得复刻 cronet 请求的信任信号（或直接用 cronet 引擎发请求）。
- **App 自身流量抓包仍盲**：okhttp 拦截器钩（含按 ClassLoader 逐份装）在真机零触发——edith 流量走 c8b.e（XYOkHttpClient，Call.Factory）→ f16.a cronet 派发，请求不经过 `RealInterceptorChain.proceed` 的常规路径（或根本不在主进程）。模拟器上 cronet 初始化失败回退 okhttp 所以能抓。
- **详情接口未回归**：`note` 子命令代码就绪（note_id+xsec_token），实测那次 App 刚好被杀，手机插回后优先补验证。

### 6.6 did 占位符事件（已还原，备查）

`xy-common-params` 里曾出现 `did=NotMainProcess-default-currentDid`：`s52/f.smali` 的 `b()` 硬编码比对进程名 `"com.xingin.xhs"`，改包名后判定失败，migo-did 不在主进程初始化。曾把 `b()` 改成恒 true 修复，后因怀疑导致首启 splash 挂起而还原。**结论：未定论，did 问题与 splash 挂起的关系待下次排查。**

## 七、第三次会战（2026-10-14）：登录也不碰手机 + 详情回归 + 模拟器复活

**原始诉求至此完整达成：登录、搜索、详情全部从 Mac 直接调 API，全程不碰手机。**

### 7.1 密码登录走 appFetch（不碰 UI）

`POST /api/sns/v4/user/login/password` 借 App 的 edith OkHttpClient 发（fetch RPC），
form = `password`(MD5 hex 小写) + `zone` + `phone` + loginparams RPC 现算的设备参数
（android_id/oaid/gaid 等 19 项）。真机、模拟器均一次 200 成功。
此前 rawfetch（HttpsURLConnection 裸发）是 461+300015；差别就在**完整拦截器链**。

注意：**账号是单会话**——新登录会把旧设备的 sid 踢失效（App 本地仍显示登录，
但请求全 -100）。模拟器登录过一次就把真机踢了，真机需重新登录。

### 7.2 x-legacy-sid 的正确形态与注入方式

- TinyInterceptor（`n0c/p.java:79`）用 `header()` **强制覆盖**
  `x-legacy-sid = n2c.b.b()`（= `IUserService.getSessionId()`）——
  往请求里 addHeader 注 sid 没用，必须钩读取点。
- 新增 `setsession` RPC：钩 `n2c.b` 的 `b()`（sid）/ `c()`（uid）返回我们的值。
  jadx 里的 `f267643a` 是别名，运行时字段名就是 `a`（静态单例）。
- sid 形态：UI 登录后 `getSessionId()` 返回 `session.<id>`；密码登录接口返回的
  `data.session` 是**裸数字 id**，当 header 用要补 `session.` 前缀
  （`secure_session` 字段里嵌着带前缀形态，可对照）。客户端 `sid_header` 属性统一处理。
- 看门狗杀掉进程后钩子失效，客户端在每次 `_wait_ready` 成功后自动重新注入。

### 7.3 详情接口实测（GET /api/sns/v1/note/imagefeed）

参数：`note_id`、`xsec_token`（搜索结果带）、`page=1`、`has_ads_tag=0`、`num=5`、
`fetch_mode=1`、`source=explore` —— 这套实测 200。
返回结构与想象不同：**`data` 是 list**，`data[0]` 下：
`note_list[0]` = 笔记本体（title/desc/images_list/time/liked），
`user` = 作者，`comment_list` = 评论。客户端 main() 的 note 分支已按此解析。
静态补充：NoteDetailService 里 imagefeed 的两个 retrofit 方法参数表都没有
xsec_token（它走的是 extra_params 或别的注入点），以实测为准。

### 7.4 模拟器路线复活（emu target）

- 模拟器上 cronet 回退 okhttp，fetch RPC 可用；登录走 appFetch 同样 200。
- Mac 直连（requests + sign RPC）在模拟器上也是 406 空响应，与 session 无关，
  确认是通道级风控。emu 现在默认也走 appFetch（`XHS_EMU_DIRECT=1` 可回直连调试）。
- emu 抖动比真机大：attach 阶段常见 `warming`（Java VM 未起）和
  `script has been destroyed`（看门狗杀进程），重跑 1-3 次可过。

### 7.5 操作纪律

- **登录是写操作且有风控计数**：一个会话周期内只登一次，session 落盘
  session.json 后复用，别每次跑都重登（本次调试误连登 3 次，侥幸没触发验证码）。
- 真机重打包 APK 重装（install -r）保留数据；但新内嵌脚本必须重装才生效
  （setsession 就是靠 rebuild 带进真机的）。

## 八、测试用例与稳定性补课（2026-10-14 下午）

### 8.1 用例：伦敦二手最近 24h 帖子抓取

`client/case_search_recent.py`：时间倒序翻搜索页 → 逐条取详情 → 按
`note_list[0].time` 过滤时间窗 → JSONL 落盘（剥 comment_list）。
实测「伦敦 二手」24h 窗口抓到 **25 条**（`client/out/伦敦二手_最近24h_合并.jsonl`）。

翻页三条经验（都踩过坑）：
1. `search_id`/`session_id` **必须一次搜索会话固定**——每页换新会被当成全新搜索，
   翻页结果大量重复（实测 50 页全是重复）。
2. 去重后必须有**停止条件**：连续 3 页纯重复 / 连续 2 页空 / 整页超窗 / 页数硬上限，
   否则 `while kept < cap` 在纯重复页上死循环。
3. `sort=time_descending` 服务端接受，最新排序过滤时间窗最高效。

### 8.2 稳定性补课（这轮新修的）

- **尸体连接**：python 客户端死后，gadget 侧的 TCP 是半开的（gadget 不主动写就
  永远发现不了宿主没了），新客户端 accept 永远等不到。修法：`_launch_gadget_tcp`
  里 App 在跑但 8s 不连入就 force-stop 重启（gadget 2s 重连周期，8s 足够判定）。
- **fetch 应用内挂死**：okhttp `execute()` 偶发永不返回，且 gFetchExec 是单线程，
  一挂之后所有 fetch 排队到天荒地老。修法：JS 侧 `future.get(45s)` 超时 +
  `shutdownNow` 重建 executor + 重找 OkHttpClient 实例；Python 侧把 TimeoutError
  纳入重连重试。
  （frida 坑：`future.get(long, TimeUnit)` 要用显式 overload + 枚举字段 `.value`，
  直接传数字会报 argument types do not match）
- **重连后必须重新 setsession**：`_reattach` 走的就绪路径原来不调 `_apply_session`，
  进程重启后钩子没了，搜索静默变游客 -100。已修。

### 8.3 仍未解决：看门狗升级疑云

当天 12:52 之后局势恶化：任何 appFetch 网络请求几乎必触发进程自杀
（12:26 同一套代码连跑 51 页+上百详情请求无事）。截图显示 App 反复停在 splash
冷启动。syscall 监控无日志 → 杀手是内联 svc 或外部 SIGKILL。疑似：
(a) 账号/设备被服务端标记后 App 收到配置指令加强了自毁；
(b) MIUI 对反复崩溃进程的限制。
**待办**：冷却一段时间（换账号/换天）再试；或继续追内联 svc 杀手
（libmsaoaidsec.so 里还有未 NOP 的分支）。

## 九、406 结论纠正 + 脱离 App 的发送守护进程（2026-10-14 下午）

### 9.1 406 的真相：不是通道指纹，是风控状态

之前判定"Mac 直连 406 = 缺 cronet 信任信号"是**错的**。三轮实验：

1. **头 diff**：appFetch 实际发出的头 vs sign() 产物，只差 `x-b3-traceid`/`x-xray-traceid`
   两个追踪头，签名类头一个不少——头不是问题。
2. **curl_cffi 仿 Chrome/Safari TLS**（Mac 直连）：仍 406——但不是 TLS 指纹（见 3）。
3. **ClientHello 抓取对比**（自建 JA3 捕获服务）：App 进程内 rawfetch 与
   app_process 守护进程的 JA3 **完全相同**（同为 Conscrypt 默认），但前者过 406、
   后者不过——**TLS/进程指纹都不是信任信号**。
4. **A/B 交替同 URL 同头**：App 内 rawfetch 与守护进程**一起从 -100 翻成 406**——
   406 是服务端风控状态开关（打热后全通道 406，冷却期全恢复）。

推论：Mac 直连在冷却状态下可能本来就通，之前每次测 Mac 直连时设备/账号已被打热。
**操作纪律：控制请求频率，406 空响应出现就停手冷却，别硬刚**（越打越热）。

### 9.2 发送守护进程（脱离 App 进程）

`tools/sender/Sender.java`：`app_process` 托管的独立 Java 进程，TCP 监听设备
127.0.0.1:27046，JSON 行协议收发 HTTP（HttpsURLConnection）。与 xhs App 无关：
**不看门狗、不自杀、不要 UI**。手机降级为"哑网络设备"。

```bash
# 部署（一次）
adb push tools/sender/classes.dex /data/local/tmp/sender.dex
adb shell "CLASSPATH=/data/local/tmp/sender.dex setsid app_process / Sender 27046 \
  > /data/local/tmp/sender.log 2>&1 < /dev/null &"
# 使用（客户端自动 ensure 拉起+forward）
XHS_VIA=daemon python xhs_api.py --target real search "咖啡"
```

形态对比：
- `XHS_VIA` 不设：签名+发送都在 App 进程内（appFetch，链最全但吃看门狗）
- `XHS_VIA=daemon`：签名借 App（sign RPC，轻量、纳秒级），发送走守护进程
  （被杀风险为零；App 只在签名瞬间需要活着，重连窗口即可完成）

下一步（未做）：把签名也搬进守护进程（System.loadLibrary 直接加载 shield/tiny
的 .so 自己算），彻底不碰 App 进程。难点是签名 native 可能校验宿主身份
（包名/签名/账号服务），需要逐个补桩。

### 9.3 补充：setsession 生效条件与模拟器天花板（2026-10-14 晚）

- **多 ClassLoader 坑**：petal 插件化下 `n2c.b` 有多份副本，钩默认 loader 线上无效。
  最终解法是钩源头 `com.xingin.account.impl.UserServiceImpl`
  （getSessionId/getUserId/isLogin 等 8 个读方法全钩），拦截器链无论从哪读都生效。
  已验证线上 `x-legacy-sid` 与 `xy-common-params` 的 sid 都变成注入值。
- **模拟器天花板**：sid 已经新鲜且线上正确（登录 appFetch 200 刚拿的），
  搜索仍 -100。xy-common-params 里 emulator 指纹明显（`cpu_name=ranchu`、
  `device_level=1`、`nqe_score` 异常）——**搜索接口不认模拟器登录态**。
  模拟器只能跑游客接口（basic homefeed ✅）。登录态搜索/详情必须真机。
- **通道敏感度的修正**：daemon 与 App 内 rawfetch 在搜索上同翻转（A/B 已证），
  但**登录接口** daemon 406 / appFetch 200——登录这类敏感 POST 的通道检查更严。
  结论：daemon 适合读取类接口（搜索/详情/首页），登录留给 appFetch。

**操作纪律结论**：一个账号一天内登录 ≤2 次、读取请求控制在低频；

## 12. 破局：mitmproxy 零插桩收割（2026-10-15 晚）

killer 专杀"对网络栈的插桩/借用"（appFetch、okhttp 钩、n0c.p 钩全部秒杀），
但**对链路中间的代理无感知**——最终路线：

### 12.1 管线

```
手机 xhsre（原生 UI 登录，零 frida 介入网络栈）
   │ 系统全局代理 settings put global http_proxy <mac>:8082
   ▼
Mac mitmdump（用户 CA 已装手机）+ mitm_harvest_addon.py
   → 目标接口响应体落盘 /tmp/xhs_harvest.jsonl
adb input 驱动 UI（搜索/滚动/点详情），parse 落盘 out/*.jsonl
```

### 12.2 关键步骤与坑

1. **CA 安装**：file:// intent 装不了（无法读取），必须走
   设置→安全→更多安全设置→加密与凭据→安装证书→CA 证书→仍然安装→文件选择器。
2. **Android 7+ 默认不信用户 CA**：重打包 APK 的 manifest 加
   `android:networkSecurityConfig`，res/xml 里 base-config 加 `<certificates src="user"/>`。
   （官方包没这个所以官方包抓不了——正好互不干扰。）
3. **域名是 rnote.com 不是 xiaohongshu.com**：edith.rnote.com / so.rnote.com（搜索）。
   之前 harvest 钩按 xiaohongshu.com 过滤也是颗粒无收的原因之一。
4. **滚动加载节奏**：搜索结果每 20 条一页，App 大约每 5-6 屏滑动手势才发一次请求，
   长滑（2050→350）效率更高；连续 8 屏无新内容=到底。
5. **详情**：deep link（xiaohongshu.com/rednote.com/xhsdiscover）实测不跳转；
   走 UI 点卡片 → NoteDetailActivity → imagefeed 自动被收割 → 返回。
6. UI 点按：xhs 自绘 UI 不吃 `input tap`，一律微滑（130ms）。
7. ADBKeyBoard 输入中文前要先 `ADB_CLEAR_TEXT`（广播是插入式，会叠加）。

### 12.3 成果

- 「伦敦 二手」列表 328 条（滚到底），字段全（note_id/xsec_token/title/desc/
  互动数/时间/图片链/作者）→ `client/out/伦敦二手_滚动收割合并.jsonl`
- 详情批量收割器 `ui_detail_harvest.py`（逐个点进笔记页，~5s/条）
- 全程零进程自杀、零 -100——原生登录态 + 代理路径对风控完全隐身

### 12.4 当前认知总结（风控）

- 账号/设备热态会过去（隔夜就好），但**重打包客户端身份被永久标记**：
  任何经我们手的协议级请求（appFetch/daemon/注入 session）都是出生即焚
- 原生 UI 登录 + App 自己发请求 = 完全正常（服务端区分"谁在发"靠的是
  请求路径上的插桩痕迹，而非账号或设备）
- 所以正确姿势：**让 App 当发射器，我们在链路上旁观**（代理收割），
  绝不替它发、绝不钩它的网络栈

## 13. 经验总结：最终操作手册（2026-10-15）

### 13.1 一句话路线

**App 当发射器，代理当旁观者，adb 当手指。**
不让 App 替你发请求（appFetch/注入），不钩它的网络栈（frida ok 钩），
只做两件"物理层"的事：adb 驱动 UI、mitmproxy 在链路上抄收。

### 13.2 为什么是这个路线（风控认知演变）

| 阶段 | 做法 | 结果 |
|---|---|---|
| 1 | Ghidra/jadx 逆出 tiny/shield 签名，Mac 直连 | 406 空响应 |
| 2 | 借 App 的 OkHttpClient 发（appFetch） | 冷账号能用，热账号/热设备秒杀进程 |
| 3 | app_process 守护进程发（绕看门狗） | 服务端同通道翻转，且敏感接口不认 |
| 4 | 注入 session 到官方存储账号 | 与注入无关，全焚 |
| 5 | pm clear 洗 did / 伪造登录参数 | 无效，标记在重打包客户端身份本身 |
| 6 | **UI 原生登录 + mitmproxy 收割** | **完全隐身，零自杀零 -100** |

核心认知：
- 风控区分"谁在发请求"靠的是**请求发起路径上的插桩痕迹**，不是账号或设备
- 热态（账号/设备）是小时级的，会自愈；**客户端身份标记是持久的**——
  但只要 App 自己正常使用，它永远是"好客户端"
- 登录接口风控故意放行（不提醒攻击者），数据接口才下刀

### 13.3 标准作业流程（SOP）

**一次性准备**（设备/环境）：
1. mitmproxy CA 推手机：设置→安全→更多安全设置→加密与凭据→安装证书→CA 证书
2. 重打包 APK manifest 加 networkSecurityConfig 信任用户 CA（`xhs-repack/` 已含）
3. 手机 `settings put global stay_on_while_plugged_in 3`（充电常亮）
4. 装 ADBKeyBoard（中文输入）

**每次收割**：
1. Mac：`mitmdump --listen-port 8082 -s mitm_harvest_addon.py`（落盘 /tmp/xhs_harvest.jsonl）
2. 手机：`settings put global http_proxy <mac_ip>:8082`；**用完必须 `:0` 撤掉**（会影响机主正常上网）
3. UI 原生登录一次（存储 session，长期有效，不要协议登录）
4. `ui_scroll_harvest.py --keyword X --scrolls N`（列表）
5. 可选 `ui_detail_harvest.py`（详情，需独占屏幕 ~5s/条）
6. `merge_details.py` + parse 落盘 out/*.jsonl

**效率参考**：列表 ~10 分钟/300 条；详情 ~30 分钟/300 条。

### 13.4 手机操作避坑清单

- **焦点铁律**：每次 input 前校验 `dumpsys window | grep mCurrentFocus` 是
  `com.xingin.xhsre`；官方包（用户私人号）在前台时绝不盲点。
  出过两次事故：焦点掉官方包搜索页、微信聊天页。

- 切 IME 会导致当前 Activity 重建，焦点可能掉到上一个任务栈
- 熄屏后 mCurrentFocus=null，gadget RPC 会 warming 超时——先亮屏解锁
- 机主要用手机立刻撤代理（`settings put global http_proxy :0`）
- 域名为 **rnote.com** 系（edith/so/rec.rnote.com），不是 xiaohongshu.com

## 14. APK 内置详情驱动（2026-10-15 深夜）

详情获取的终极形态：**把驱动做进 APK**，让 App 用自己的 service 层发详情请求，
速度不再受 UI 点按约束。

### 14.1 架构

```
am broadcast -a com.xhsre.driver.FETCH_DETAILS -p com.xingin.xhsre -f 0x00000020
  --es path /sdcard/Android/data/<pkg>/files/q.txt --el interval 3000
   ▼
DetailFetchReceiver（新增 smali_classes21，manifest 注册 exported receiver）
  → 读队列文件（note_id 一行一个）
  → rv9.c.a.b(NoteDetailService.class)   // App 自己的 DI 拿 edith retrofit 服务
  → queryNoteDetailFeedData3Up(note_id,1,false,5,1,"search","","","",false,"")
  → .subscribe(Observer)                  // 不加 subscribeOn：retrofit 在调用线程同步执行
   ▼ 请求走 App 原生签名/会话/线程（与 UI 点开完全同构）
mitmdump 旁路收割响应体（同 §12）
```

### 14.2 实现要点（全是坑）

- **DI 入口**：`rv9.c` 单例的 `b(Class)` 方法（edith host）；字段名是 `a`——
  **jadx 的 f320874a 是消歧后缀，运行时真名看 smali**（老坑，§9.3 同型）
- **service 接口**：`com.xingin.notebase.notedetail.service.NoteDetailService`
  `queryNoteDetailFeedData3Up`（imagefeed，11 参数）
- **App 的 rxjava 是裁剪版**：有 `Observable.subscribe()/subscribe(Observer)`，
  **没有 Schedulers/Consumer**；`Observer.onSubscribe` 参数是 `h4d.c`（裁剪后的
  Disposable）——stub 必须按运行时签名写，否则 AbstractMethodError
- **不加 subscribeOn**：retrofit rx 适配器在调用线程同步发 HTTP，驱动线程天然串行
- **队列文件位置**：`/sdcard/Android/data/<pkg>/files/`——/sdcard/Download 应用无权读
- **广播收不到**：包处于 stopped 状态时必须带 `-f 0x00000020`（INCLUDE_STOPPED）
- **编译链**：javac(stub+android.jar) → d8 → baksmali → decoded/smali_classes21
  → manifest 注册 receiver → apktool b
- stub/源码在 `xhs-repack/driver/`

### 14.3 风控表现

- ~40 条/次 进程必被看门狗杀（1.2s 和 3s 间隔都一样，杀的是"密度"不是"间隔"）
- 杀了不封号、不焚 session，App 重启后续跑完全正常
- 应对：编排器 `run_detail_batch.py` 按"已捕获差集重推队列+重广播"循环，
  实测 ~4.5 条/分钟稳定推进，328 条约 70 分钟（全自动无需看守）

### 14.4 与 UI 点按对比

| | UI 点详情 | APK 内驱动 |
|---|---|---|
| 速度 | ~5s/条 | ~1s/条（被杀前） |
| 屏幕 | 独占 | 不需要 |
| 稳定性 | 翻页/视频页各种意外 | 队列驱动，幂等续跑 |
| 风控 | 同样会杀（密度） | 同样会杀，自动恢复 |

### 14.5 风控升级实录：账号异常（2026-10-15 22:45）

APK 内驱动批量跑详情，3s 间隔下推进到 ~130 条时服务端把账号 2 打为
**「账号异常，请稍后重试」（code 300011）**——之后所有 imagefeed 返回
300011 空体，进程不再被杀（账号级封控替代进程级）。

- 立即停手：撤代理、force-stop、编排器终止
- 已入仓不受影响：71 条有效详情 + 328 条全量列表
- 账号 2 处置：冷却不碰（不登录不请求）。300011 是**警告级**不是封号，
  冷却（小时~天级）后可恢复，恢复后正常使用

**教训修正（2026-10-16）：限的是分钟级频度，不是日总量。**

两组实测对照：

| 持续速率 | 持续时间 | 结果 |
|---|---|---|
| ~20 条/分钟（3s 间隔连发） | ~6.5 分钟（~130 条） | 300011 账号异常 |
| ~4.5 条/分钟（含杀进程重启摊薄） | 70+ 分钟（71 条） | 无任何异常 |

结论：触发线是**持续分钟级速率**（在 5 和 20 条/分钟之间，待爬坡实测定位），
不是日累计量。单号日天花板大概率远高于此前估计的 60——只要速率压住。
进程杀（~40条/生命周期）只是前奏，与间隔无关；账号级异常才是真天花板。
要跑量仍可池化接力（keman 模式：多机×多克隆×多号轮换），
但单号低速长跑可能比预想能扛得多。

### 14.6 流控设计（2026-10-16 修正：分钟级限速为主）

`run_detail_batch.py` 流控参数（主控 = 持续速率 ≤ proven-safe 线）：

| 参数 | 值 | 依据 |
|---|---|---|
| 条间间隔 INTERVAL | 8000-15000ms 随机抖动 | 4~7.5 条/分钟，对齐 4.5条/分钟 proven-safe 线 |
| 批大小 ROUND_CAP | 20 条 | 进程杀线 ~40，留一半余量 |
| 批间停顿 ROUND_PAUSE | 180-300s 随机 | 进一步摊薄平均速率到 ~3-4 条/分钟 |
| 日封顶 DAILY_CAP | 300 条/号（兜底） | 日总量天花板未测出，主控是分钟级速率 |
| 停滞熔断 | 100s 无进展当天停手 | 杀进程/账号异常的前兆，不顶格试探 |

**待办：爬坡实测定位速率触发线。** 账号恢复后按 5 → 8 → 12 → 16 条/分钟
逐级各跑 20 条（级间停 5 分钟），出现任何异常立即停。找到膝点后
把 INTERVAL 校准到膝点的一半。

### 15.2 用户 CA 安装的连环坑（全部趟过，按顺序）

1. **锁屏前置**：EMUI 安装用户证书前强制设锁屏图案，安装时还要再画一次
   确认（ConfirmLockPattern）。设了图案后记得 `svc power stayon true`，
   否则 UI 自动化会被锁屏挡住。
2. **手机时钟必须是当前时间**：机器初始日期 2020-03-02，证书会
   "不在有效期内"。`settings put global auto_time 1` 几秒后自动校准。
3. **adb push 的文件不进 MediaStore**：DocumentsUI（从SD卡安装）和华为
   文件管理都看不到刚 push 的 .cer；`MEDIA_SCANNER_SCAN_FILE` 广播无效。
   重启手机可强制全量扫描，但有更轻的路（见 4）。
4. **正解（免重启、可全脚本化）**：
   ```bash
   adb push ~/.mitmproxy/mitmproxy-ca-cert.cer /sdcard/
   adb shell "cp /sdcard/mitmproxy-ca-cert.cer /data/local/tmp/m.cer && chmod 666 /data/local/tmp/m.cer"
   adb shell am start -a android.intent.action.VIEW -d file:///data/local/tmp/m.cer \
     -t application/x-x509-ca-cert -n com.android.certinstaller/.CertInstallerMain
   ```
   注意：/sdcard 是 FUSE 不支持 chmod（CertInstaller 读不了 -rw-rw----），
   必须借 /data/local/tmp（真文件系统，shell 可 chmod 666）。
   sdcard 路径直投会报"安装失败。无法读取证书文件"。
5. 命名对话框：名称栏用 ADBKeyBoard `ADB_INPUT_B64` 注入，凭据用途保持
   默认"VPN 和应用"，点确定。
6. **验证**：浏览器开 `https://edith.rnote.com`，无证书警告直接出
   nginx 页 = 链路全通。
